## 18. Актуальная модель разрешений Florial Manager — 03.11.2026 (после реализации)

Этот раздел дополняет и уточняет раздел 16.4 и supersedes его формулировки, если они расходятся с фактически внедрённой моделью. Текущий рабочий источник — `main` репозитория `omaraandrey-dev/florial`, файлы `functions/api/manager/*`, `src/manager/*` и D1 migration `0006_manager_permissions.sql`.

### 18.1. Текущие независимые права

В `catalog_staff_profiles.permissions` хранятся десять boolean-флагов:

- `canCreatePlant` — создание и отправка собственных черновиков растений;
- `canEditPlantCard` — подготовка и редактирование финальной карточки, включая связанные AI-процессы;
- `canAddPlantVariant` — добавление вариантов существующего растения;
- `canEditPlantPrice` — изменение цены существующего варианта;
- `canReviewPlantSubmissions` — просмотр очереди проверки, возврат на исправление и отклонение;
- `canApprovePlantSubmission` — одобрение подготовленной заявки;
- `canPublishPlant` — окончательная публикация одобренной заявки в Sanity;
- `canManageStaff` — создание и управление сотрудниками, которых создал этот менеджер;
- `canDelegatePermissions` — назначение другим сотрудникам подмножества собственных разрешений и создание другого менеджера;
- `canViewAnalytics` — просмотр аналитики сайта.

Роль `owner` автоматически имеет все права независимо от значений JSON-флагов. Для `manager` и `seller` проверяются персональные разрешения. Интерфейс скрывает недоступные действия, но единственной границей защиты остаются серверные проверки каждого API.

### 18.2. Делегирование и границы полномочий

- Для управления сотрудниками требуется `canManageStaff`.
- Для назначения/изменения разрешений и создания сотрудника с ролью `manager` дополнительно требуется `canDelegatePermissions`.
- Менеджер может передать только те разрешения, которыми обладает сам; сервер отклоняет попытку повышения полномочий.
- Менеджер может управлять только профилями, созданными непосредственно им (`created_by`). Профили, созданные владельцем до миграции 0006, остаются под управлением владельца.
- Менеджер не может изменять собственный профиль или профиль владельца.
- Роль `seller` не может получить права финального редактирования, проверки, одобрения, публикации, управления сотрудниками, делегирования или аналитики.
- Выдача и изменение разрешений записываются в `catalog_staff_permission_events`: actor, target, action, старый/новый набор прав, timestamp.

### 18.3. Разделение проверки, одобрения и публикации

Одобрение и публикация — разные действия. `canApprovePlantSubmission` разрешает перевести заявку в `approved`, только если финальная версия карточки уже подготовлена и сохранена. `canPublishPlant` разрешает публикацию в Sanity только из статуса `approved` (или безопасный повтор после `publish_failed`). Менеджер может иметь одно из этих прав без второго. Для изменения существующего растения в Sanity требуются и одобрение, и публикация.

Менеджер с `canCreatePlant` может создать и отправить собственную заявку на проверку. Для финального редактора и связанных AI-процессов требуется `canEditPlantCard`. Возврат на исправление/отклонение проверяется отдельно через `canReviewPlantSubmissions`.

### 18.6. Раздельная публикация изменений существующих растений

Заявки на добавление варианта и изменение цены проходят отдельные переходы:

1. `submitted` / `in_review` → `approved`: требуется `canApprovePlantSubmission`. Сервер проверяет текущую ревизию документа Sanity, но не изменяет публичный каталог.
2. `approved` / `publish_failed` → `published`: требуется `canPublishPlant`. Только этот шаг изменяет Sanity.

Публикация повторяемая: если Sanity уже содержит именно запрошенный вариант или цену, но обновление статуса D1 ранее завершилось ошибкой, повторный запрос подтверждает уже применённое изменение и завершает статус без дублирования.

Если финальная карточка нового растения редактируется после `approved` или `publish_failed`, статус автоматически возвращается в `in_review`, сбрасываются отметки предыдущего одобрения/публикации и требуется новое одобрение. Общий endpoint Manager не может обходить специальные endpoints для установки статусов `published`, `publishing`, `publish_failed` и для одобрения заявок изменения существующих растений.

- `FL-TEST-20261103-04`.

На момент выпуска все четыре тестовых заказа остаются в Production и доступны для проверки интерфейса. Не удалять их без отдельного поручения владельца.

## 23.1. Product SEO — единый стандарт карточек всех товаров

Языки: BG, RU, EN. Поля активные, рабочие и редактируемые непосредственно в существующей Sanity Studio.

### Поля Sanity

- Отдельный object type `productSeoFields` содержит `h1`, `metaTitle`, `metaDescription`, `noIndex`, `keywords`.
- Корневое поле `seo` — основная болгарская версия; SEO языков RU/EN находится в `translations.ru.seo` и `translations.en.seo`.
- `metaTitle` имеет validation warning при длине более 70 символов.
- В product schema **нет** поля/блока `suggested` и нет «Предложения SEO». Для карточек товаров сразу заполняются реальные активные H1, Meta Title и Meta Description.

### Формат H1 и Meta Title

- H1 — отдельный, локализованный, полный заголовок карточки товара; не сокращать ради ограничения Meta Title.
- Meta Title: `Название товара | Геолокация | Градински център Флориал`.
- Разделитель — вертикальная черта `|`, не `/`.
- Максимальная длина Meta Title — 70 символов.
- Если полная брендовая подпись не помещается, использовать короткий вариант «Флориал» для BG/RU и `Florial` для EN.
- Если после сокращения бренда длина всё ещё превышена, сокращать только хвост названия по границе целого слова, сохраняя модель/основное название. Не разрывать слова. H1 и Meta Description сохраняют полное название товара.

### Формат Meta Description и география

- Начинать с коммерческого сообщения о продаже: BG — «Продажба на…», RU — «Продажа…», EN — «For sale…».
- Указать название товара, только подтверждённую краткую характеристику, локализованное имя садового центра Florial и одну естественную географическую привязку.
- Не использовать keyword stuffing, не перечислять все города в каждом описании, не придумывать свойства/наличие/доставку.
- Разрешённая география: Несебър, Равда, Слънчев бряг, Свети Влас, Поморие, Бургас, Ахелой, Каблешково, Кошарица и соответствующие локализованные написания RU/EN.
- **Созопол / Sozopol исключён** из product SEO генератора.
- Геолокация сначала определяется по первому релевантному упоминанию в описании товара и существующих SEO-текстах; если упоминания нет — выбирается детерминированно по стабильному порядку документов.
- Повторяющиеся геофразы удаляются из краткой характеристики без потери смысла; предложения, содержащие исключённую географию, не переносятся в Meta Description.
