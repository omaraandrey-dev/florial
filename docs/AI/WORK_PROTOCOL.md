# Florial — рабочий протокол

## До начала
Проверить SHA main, последние commits и открытые PR. Прочитать AI_INSTRUCTIONS, START_HERE, MASTER_SPEC, OPEN_QUESTIONS, changelog и релевантные части паспорта. Зафиксировать цель, критерии готовности, scope и затрагиваемые сервисы. До существенных изменений объяснить владельцу план и риски.

## Доказательства
Проверять исходники, тесты, package scripts, workflows, конфигурации и относящиеся к задаче живые Sanity/Cloudflare/Resend сервисы. Записывать точные commit SHA, run ID, deployment ID, dataset и document ID. Документ не доказывает текущее состояние live service.

## Статусы
- **Проверено по коду** — конкретный commit и файлы.
- **Проверено в живом сервисе** — read-only запрос или безопасный smoke test.
- **Проверено тестом/CI** — точный run и commit SHA.
- **Не подтверждено** — нет достаточного доказательства.
- **НЕ ИЗВЕСТНО — нужно уточнить** — не хватает данных или решения владельца.

## Защита услуг, блога и портфолио
Существующие опубликованные `service`, `blogPost` и документы портфолио нельзя редактировать, заменять, переименовывать, деактивировать, снимать с публикации или удалять без отдельного явного подтверждения владельца. Сначала показать точный план (ID, slug/URL, поля, изображения, ссылки и последствия) и дождаться подтверждения. До него разрешены только read-only проверки; не выполнять Sanity write. Согласование одной страницы не распространяется на остальные. Новую страницу создавать отдельно, не перезаписывая старую, если владелец прямо не распорядился иначе.

## SanityПеред write определить project/dataset/document ID, сохранить backup затрагиваемых документов, выполнить только согласованную запись и перечитать результат. Не публиковать schema/documents без согласования. AI-рекомендацию пригодности к Черноморскому побережью не выдавать за подтверждённый статус сотрудника.

## Cloudflare D1
Отличать migration SQL в GitHub от реально применённой миграции. До write проверить live schema и migration ledger. Dry-run выполнять изолированно. Production migrations, destructive operations, retention и изменения данных требуют разрешения. Supabase SQL не является D1 migration.

## CI/deployment
Проверять workflow именно для точного SHA. Проверять Pages deployment и его commit SHA. Если Preview выключен, не заявлять о наличии Preview. Не создавать production orders, emails или data writes в smoke tests без согласования.

## Единая схема веток Florial

- `main` — Production и стабильная версия сайта.
- `develop` — единственная постоянная ветка развития всего сайта. Все направления разработки ведутся последовательно в ней; обычные task-specific ветки не создаются.
- Новая работа начинается от актуального HEAD `develop`, после проверки незавершённых изменений. Не начинать от устаревшего SHA.
- Релиз: PR `develop → main`; перед ним exact-SHA CI, Preview, функциональные и безопасные smoke-проверки, review diff и согласование владельца. После merge проверить Production deployment и raw HTTP smoke.
- После релиза синхронизировать `develop` с новым `main` обычным fast-forward/merge без force-push и потери новых коммитов.
- Существующие task-specific ветки и открытые PR — переходные исключения, которые завершаются по текущему плану. Не создавать новые параллельные ветки.
- Исторические refs не чистить массово и не восстанавливать без прямого указания владельца.
- Общую документацию редактировать последовательно, одним интеграционным потоком. Перед каждым изменением перечитывать актуальный файл и проверять diff.
- PR #409 закрыт владельцем как временный/устаревший. Не использовать его head, diff, ветку или Preview как актуальную основу; не переносить его изменения и не возобновлять этот PR. Общие документы редактировать последовательно в `develop` по текущему протоколу, сверяясь с актуальным `main`.

## Cloudflare: сохранённые legacy-переменные
Владелец подтвердил 18.11.2026, что `SUPABASE_*` / `VITE_SUPABASE_*` в Cloudflare Pages — намеренно оставленные dormant-переменные «на всякий случай», не используемые Florial. Не считать их действующей интеграцией, не проводить повторный аудит только из-за их наличия, не удалять/не менять и не читать их значения. Возможная активация Supabase — отдельное будущее архитектурное решение с новым явным согласованием.

## Работа с изменениями и документацией

- Перед правкой зафиксировать цель, критерии готовности, затрагиваемые файлы/сервисы и риски.
- Не выполнять параллельные изменения одного общего документа.
- После каждого законченного этапа проверить полный diff, ссылки, отсутствие секретов и сохранность прежних записей.
- Временно открытые PR/ветки завершать без создания новых параллельных веток; после интеграции продолжать в `develop`.
- При конфликте остановиться и вручную сверить обе версии; не удалять чужие записи и не force-push.
 
## PR и завершение
Проверить diff, ссылки, секреты и scope. PR описывает изменения, проверки, ограничения и незавершённые действия. Merge/Production release — только при явном разрешении. Обновить CHANGELOG, Technical Passport и Open Questions.
