## Дополнение rev64 — подтверждение фактической записи нового размера растения

- Для сценария выбора существующего растения по совпадению (красная точка) и добавления нового размера API `POST /api/manager/plants/:id/add-variant` должен после Sanity mutation повторно прочитать целевой документ и подтвердить, что в `saleVariants` присутствует именно переданный вариант.
- Подтверждение выполняется по `_key`, `name`, `priceEUR`, `stockStatus=inStock` и `stockQuantity`. Одной новой `_rev` недостаточно для признания операции успешной.
- API возвращает `ok=true` и `variantVerified=true` только после полного совпадения. При отсутствии или несовпадении варианта возвращается безопасный код `SANITY_VARIANT_NOT_CONFIRMED`; Manager не должен закрывать форму и показывать сообщение об успешном сохранении.
- Повтор операции с тем же idempotency key обязан повторно проверить документ Sanity. Если вариант уже присутствует и совпадает, повтор не добавляет дубликат. После временной ошибки read-back допускается повторная проверка и безопасное продолжение по исходному idempotency key.
- Manager UI дополнительно проверяет `ok`, `variantVerified`, ожидаемый `documentId` и непустую `revision` до вызова success callback.
- Добавить unit tests для совпадающего, отсутствующего и несовпадающего варианта. Сохранять полный audit snapshot документа; не сокращать его до projection, если это приводит к потере данных в журнале.
- Изменения этого этапа ограничиваются add-variant API, helper/типами, PlantDuplicatePicker, тестами, `docs/TECHNICAL_PASSPORT.md` и `CHANGELOG.md`. Не менять Sanity schema/documents/assets, D1 schema/rows, Cloudflare secrets/settings, оборудование, заказы, Header, меню, Footer или глобальную структуру.
- Не выполнять production writes для тестирования без отдельного прямого согласия владельца. После публикации требуется авторизованный live-тест владельцем на отдельной/согласованной карточке растения.
