# Florial Manager — единое управление каталогом растений

**Версия:** 1.0  
**Дата:** 09.11.2026  
**Статус:** техническая спецификация согласована; реализация не начата  
**Область:** только Sanity project `bxvcy0qs`, dataset `plants`, документы `product` и `category`.

> Это техническое задание заменяет для будущей реализации растений прежний сценарий обязательной приёмки и публикации Owner. Оно не является разрешением на запись в Production, применение D1 migration, изменение Sanity schema или deployment. Эти действия выполняются отдельными этапами после проверки и согласования плана.

## 1. Решения владельца

1. Каталог Manager в этой задаче работает **только с растениями** из Sanity dataset `plants`.
2. Роли `owner`, `manager`, `seller` могут самостоятельно создавать, редактировать и напрямую публиковать растения.
3. Редактирование существующих растений — **all**: все три роли могут редактировать любую карточку, а не только созданную ими.
4. Публикация — **direct**: нет промежуточного одобрения Owner/Manager и нет обязательной заявки на публикацию.
5. История действий доступна **только Owner**; серверная проверка обязательна.
6. Общая кнопка AI-заполнения доступна всем трём ролям.
7. Раздел/действие ботанического исследования и поля биологических свойств скрыты от Seller и Manager; доступны Owner. Для не-Owner сервер также запрещает изменять эти поля и сохраняет прежние значения.
8. Owner не должен вручную принимать каждую новую карточку. Сотрудник отвечает за корректность введённых данных и публикацию.
9. Основной интерфейс — мобильный телефон; desktop остаётся поддерживаемым.
10. Публичные Header, меню, Footer, корзина, checkout и каталог оборудования не входят в объём задачи.

### 2.2 Важное наблюдение по старым данным

В выборке опубликованных растений обнаружены карточки, у которых корневой `priceEUR` отличается от `saleVariants[].priceEUR` (например, у `citrus-kumquat`: корневое значение 3000, вариант — 25). У некоторых карточек также различается корневой статус и статус варианта.

Поэтому:
- нельзя массово переписывать корневые цену/наличие при открытии или сохранении карточки;
- перед реализацией нужно проследить фактическую логику цены и наличия в публичных Category/Product/cart/order компонентах;
- вариантные значения должны сохраняться без потери;
- правило агрегирования цены/наличия для списка Manager должно быть определено после проверки публичного контракта;
- любые legacy значения, которые не входят в изменяемый пользователем набор, остаются нетронутыми.

## 3. Целевая модель интерфейса

### 3.1 Экран «Растения»

Единый экран для всех ролей:
- заголовок «Растения»;
- поле поиска;
- кнопка фильтра/сортировки;
- категории и подкатегории;
- количество найденных карточек;
- список растений;
- закреплённая снизу кнопка «Добавить растение».

Карточка в мобильном списке:
- thumbnail слева;
- название справа;
- цена под названием;
- статус: «В наличност», «По заявка» или «Изчерпан»;
- компактное меню действий;
- нажатие на строку открывает редактор.

Поиск:
- название;
- ботаническое название;
- SKU;
- локализованные названия, если они заполнены.

Фильтрация:
- категория;
- подкатегория;
- статус наличия (как дополнительный быстрый фильтр, если он не усложняет мобильный экран).

Сортировка:
- по дереву категорий/названию категории;
- по названию внутри категории.
Не добавлять сложные сортировки по цене/остатку в первую версию, если владелец отдельно их не запросит.

Загрузка списка — постраничная, с серверным лимитом. Не загружать все изображения и полные Portable Text описания в список.

### 3.2 Редактор растения

Порядок блоков на мобильном экране:

1. **Фотографии** — основная фотография, остальные изображения, добавление, удаление из карточки, изменение порядка, выбор основной.
2. **Название** — BG как основной язык, ботаническое имя, slug (автоматическое предложение с возможностью ручной коррекции).
3. **Цена и варианты** — один вариант по умолчанию; действие «Добавить размер/вариант» для дополнительных позиций.
4. **Описание** — BG, RU, EN; краткое и полное.
5. **AI-заполнение** — кнопка доступна всем трём ролям; AI выдаёт черновик, сотрудник проверяет и применяет.
6. **Категории** — выбор существующих категорий Sanity, отображение родительской категории.
7. **Характеристики товара** — только коммерческие/витринные параметры, не биологические care fields.
8. **Наличие** — статус и количество по каждому варианту.
9. **SEO** — BG/RU/EN.
10. **Биологические свойства / ботаническое исследование** — Owner-only; полностью скрыто от Seller/Manager.

Кнопки сохранения и публикации должны быть понятны на мобильном экране. При создании — «Запази и публикувай» с подтверждением публикации. При редактировании — «Запази промените». Система не должна требовать отдельного Owner approval.

### 3.3 Фотографии

- Использовать текущий безопасный серверный путь загрузки Sanity assets и существующую библиотеку изображений, если она соответствует требованиям.
- В UI все изображения представлены единым упорядоченным списком; одна отмечена основной.
- При сохранении основное изображение записывается в `mainImage`, остальные — в `gallery` с сохранением порядка.
- Для каждой фотографии сохранять ALT BG/RU/EN.
- Удаление фотографии из карточки удаляет только ссылку из документа; сам Sanity asset автоматически не удалять.
- Не менять и не терять чужие/существующие asset references при редактировании.
- Публикация блокируется, если выбранная основная фотография невалидна или не загрузилась.

### 3.4 Варианты продажи

Использовать существующий массив `saleVariants`, до 30 вариантов. Один вариант создаётся по умолчанию; дополнительные добавляются явно.

Для каждого варианта:
- стабильный `_key`;
- название/размер свободным текстом (например, «Височина 120–140 см», «Контейнер C30», «Компактен размер»);
- `saleHeightCm` — необязательное числовое значение для совместимости/фильтрации;
- `containerVolumeL` — необязательное число;
- SKU варианта;
- цена EUR с включённым ДДС;
- старая цена при скидке;
- статус наличия;
- количество.

Свободный текст варианта — основное отображаемое название. Не заставлять сотрудника вводить только числовую высоту. Не генерировать коммерческие значения AI.

Удаление варианта из UI должно требовать подтверждения. Перед сохранением проверять минимум один вариант, максимум 30, уникальность `_key`, валидность цены и статуса.

### 3.5 Цена и наличие

- Валюта — EUR.
- Публичная потребительская цена включает ДДС; существующее `vatIncluded` не выключать.
- Вариантная цена `saleVariants[].priceEUR` является источником цены конкретного размера.
- Корневые legacy поля `priceEUR`, `oldPriceEUR`, `stockStatus`, `stockQuantity` не пересчитывать автоматически до подтверждения фактической логики storefront.
- Сохранение одного варианта не должно обнулять значения других вариантов.
- При статусе `inStock` требуется валидная цена и положительное количество, если именно так подтверждается текущим публичным/заказным контрактом. Это правило проверить в коде checkout и заказа до включения серверной валидации.
- `onRequest` может использоваться без цены, если текущий storefront это поддерживает.
- Количество может быть дробным только если действующий формат учёта растений это допускает; текущий schema `stockQuantity` — number, а UI/валидация должны быть сверены до реализации.

## 4. AI-заполнение

### 4.1 Общая кнопка — все роли

AI может предложить:
- локализованные названия и краткие описания;
- полные описания BG/RU/EN;
- переводы;
- ALT для изображений BG/RU/EN;
- SEO title/description BG/RU/EN;
- slug suggestion;
- коммерчески нейтральные характеристики из достоверного описания.

AI не должен придумывать или менять:
- цены, скидки, SKU;
- размер/высоту продаваемого экземпляра;
- остатки и статус наличия;
- категорию без выбора/подтверждения сотрудника;
- обещания доставки, гарантий и наличия.

Результат всегда предварительный. Применение AI результата — явное действие сотрудника. До сохранения показывать, какие поля будут изменены.

### 4.2 Биологические данные — Owner-only

Для Seller и Manager:
- скрыть UI раздела `plantCare` и `careGuide`;
- скрыть кнопку отдельного ботанического исследования/GBIF;
- AI endpoint не должен возвращать или сохранять эти поля для не-Owner;
- серверный PATCH обязан игнорировать/отклонять попытки прислать эти поля;
- при редактировании существующего растения их значения остаются неизменными.

Для Owner:
- сохранить существующий отдельный workflow ботанического исследования;
- отображать его в отдельном Owner-only разделе;
- результат AI/GBIF остаётся предложением, не считается подтверждённым ботаническим фактом до проверки.

Физическое удаление Sanity document не входит в первую версию. Использовать `isActive=false` как мягкое скрытие из магазина. Действие должно быть подтверждаемым и записываться в аудит. Возврат в магазин — `isActive=true`. Не удалять товар, если на него ссылаются существующие заказы или другие документы.

## 6. Целевые API-контракты

Ниже — проектируемые контракты, не существующие сейчас endpoints. Имена файлов и окончательные типы сверить с Cloudflare Pages routing при реализации.

### 6.1 Список и создание

`GET /api/manager/plants`

Query:
- `q?` — поиск по name/scientificName/SKU/локализованным именам;
- `categoryId?` — категория или подкатегория;
- `sort=category|name`;
- `cursor?`, `limit?` (default 30, hard max 100).

Response:
- `items[]`: `_id`, `_rev`, `name`, `scientificName`, `sku`, `slug`, category ID/name/parent, thumbnail, компактные variant summaries, derived list price/status;
- `nextCursor`;
- `total?` только если count не делает запрос чрезмерно дорогим.

`POST /api/manager/plants`

Body:
- `idempotencyKey`;
- `product` — allowlisted поля Sanity product, включая варианты и изображения.

Сервер:
- проверяет сессию/роль;
- валидирует поля и ссылки на опубликованные категории dataset plants;
- проверяет slug collision;
- генерирует новый document ID;
- создаёт опубликованный Sanity document напрямую;
- создаёт audit intent до Sanity mutation и результат после неё;
- возвращает `{ok, documentId, revision}`.

### 6.2 Чтение и редактирование

`GET /api/manager/plants/:id`

Возвращает полную карточку, включая варианты и локализации. `plantCare` и `careGuide` включаются только для Owner.

`PATCH /api/manager/plants/:id`

Body:
- `expectedRevision` — обязательный Sanity `_rev`;
- `idempotencyKey`;
- `set` — allowlisted поля/объекты;
- `unset?` — только явно разрешённые поля.

Сервер:
- проверяет активную сессию и роль;
- повторно читает текущий документ;
- проверяет `expectedRevision`;
- формирует минимальный patch только для изменяемых полей;
- использует Sanity `ifRevisionID`;
- не заменяет весь документ целиком;
- не трогает неизвестные/legacy поля;
- для не-Owner запрещает `plantCare`/ `careGuide`;
- пишет аудит с изменёнными полями и ограниченным before/after;
- возвращает новую `_rev`.

Конфликт ревизии возвращает HTTP 409 с сообщением обновить карточку и повторно применить изменения. Никакого silent last-write-wins.

### 6.3 AI

`POST /api/manager/plants/ai-enrich`

Body:
- краткие исходные сведения о растении;
- выбранная категория;
- варианты/цены передаются только как read-only контекст, не как поля для генерации;
- ссылки на уже загруженные Sanity image assets при необходимости.

Response:
- `suggestion` с разрешёнными текстовыми/SEO/ALT полями;
- `changedFields[]`;
- `warnings[]`;
- `diagnostics` без секретов.

AI endpoint не пишет в Sanity и не сохраняет черновик в старой таблице submissions. UI применяет ответ локально; затем сотрудник сохраняет карточку обычным PATCH/POST. Для Owner-only botany research — отдельный защищённый endpoint/действие.

### 6.4 История

`GET /api/manager/plant-audit`

Owner-only. Фильтры: `productId?`, `actorId?`, `action?`, `from?`, `to?`, `cursor?`, `limit?`.

Response: события с автором, ролью на момент действия, названием/ID растения, типом операции, списком изменённых полей, кратким before/after, временем, результатом и request ID.

Seller/Manager получают HTTP 403 даже при прямом вызове API.

## 7. Sanity write model и защита данных

- Sanity dataset для этой задачи всегда `plants`; не принимать dataset от браузера.
- Использовать серверный `SANITY_API_TOKEN`; секрет не передавать в клиент.
- Перед записью проверять category references в том же dataset.
- При создании использовать новый уникальный document ID и idempotency key, чтобы повтор запроса не создавал дубликат.
- При редактировании — `ifRevisionID`.
- Patch только изменённых allowlisted полей; не делать `createOrReplace` существующего документа.
- Не очищать поля, которых нет в запросе.
- Не удалять assets.
- Не менять `_id`, `_type`, slug или category references автоматически без явного значения сотрудника.
- Публичный storefront остаётся источником отображения товара; Manager должен соблюдать его фактический контракт по ценам, наличию и вариантам.

## 8. D1 audit log

Предлагаемая новая таблица: `manager_product_audit` (название окончательно проверить на отсутствие существующей таблицы/конфликта).

Поля:
- `id` — UUID;
- `request_id` / `idempotency_key`;
- `actor_id` — FK на `catalog_staff_profiles`;
- `actor_role` — роль на момент действия;
- `product_id` — Sanity document ID;
- `product_name` — snapshot названия;
- `action` — create/update/publish/deactivate/reactivate;
- `changed_fields` — JSON array;
- `before_data`, `after_data` — ограниченный JSON только по затронутым полям;
- `result` — started/success/failed;
- `error_code` — безопасный код без токенов/секретов;
- `created_at`.

Индексы:
- product + created_at DESC;
- actor + created_at DESC;
- idempotency_key UNIQUE;
- created_at DESC.

Append-only: запретить UPDATE/DELETE через D1 triggers и не предоставлять mutation API для журнала. Для распределённой операции Sanity+D1 использовать две append-only записи: intent/started до Sanity mutation и success/failed после. Если финальная запись не прошла, первая запись остаётся для reconciliation; endpoint не должен скрывать частичный результат и обязан вернуть request ID для повторной сверки. Действие нельзя считать полностью завершённым, пока его результат не отражён в аудите.

История доступна только Owner: серверный API фильтрует/проверяет роль до чтения строк. Не полагаться на сокрытие вкладки в UI.

Не хранить токены, пароли, сессионные данные, полные HTTP headers, приватные ошибки провайдера. Before/after ограничить полями товара, не записывать лишние персональные данные.

### 8.1 Существующие журналы не заменять

- `catalog_submission_events` остаётся историей старого workflow заявок.
- `catalog_stock_events` остаётся историей прежних операций изменения остатков.
- `catalog_staff_permission_events` остаётся журналом изменения прав сотрудников.
- Новая история прямых изменений растений — отдельный `manager_product_audit`.
- Не удалять и не мигрировать старые строки в новую таблицу без отдельного плана и подтверждения.

## 9. Переход от старого workflow

Переход должен быть постепенным и обратимым.

1. Зафиксировать текущую версию main и сделать read-only backup/сверку схем и выборки старых submissions.
2. Разработать новый прямой API и интерфейс рядом с существующими формами; старые endpoints не удалять.
3. Новая вкладка/экран начинает работать с Sanity `plants`, а не с `catalog_submissions`.
4. Все существующие опубликованные Sanity products остаются на месте; ID, slug, references, assets и варианты сохраняются.
5. Незавершённые `catalog_submissions` и `catalog_submission_events` остаются доступными в старом разделе до отдельной обработки. Не auto-publish и не auto-delete.
6. Старые формы добавления/редактирования/остатков отключаются только после проверки всех их сценариев в новой системе.
7. Старые API и D1 tables удалять нельзя в рамках первой версии. Решение об их удалении/архивации — отдельная задача после инвентаризации зависимостей.
8. Включение нового экрана — контролируемый rollout; возможность вернуться к старому экрану сохраняется до ручной приёмки Owner.
9. Не выполнять production migration и deployment без отдельного согласования и проверки CI/Preview.

## 10. Безопасность, ошибки и устойчивость

- Все write endpoints: POST/PATCH, same-origin, JSON size limit, authentication, active profile, role authorization, server-side validation, no-store.
- Защита от CSRF через текущие same-origin checks; не принимать произвольный Origin.
- Ограничить payload, число изображений и размеры файлов.
- Повторный запрос с тем же idempotency key не создаёт дубль.
- При Sanity 401/403/5xx не показывать успешное сохранение; безопасная диагностика с request ID.
- При D1 audit failure до Sanity mutation — не выполнять запись в Sanity.
- При конфликте _rev — HTTP 409; показать обновлённую версию и предложить повторно применить локальные изменения.
- При неудаче загрузки фото не терять уже загруженные и связанные с карточкой assets.
- Ошибки интерфейса и статусы — на болгарском языке.
- Все операции аудита фиксируют фактического сотрудника и роль из серверной сессии.

## 11. План реализации и критерии приёмки

### Этап A — storefront contract и тестовые данные (read-only)
- проследить цену/наличие/варианты по CategoryPage, ProductPage, cart, checkout и order validation;
- проверить slug routing и category references;
- проверить существующие поля/legacy fallback;
- определить точную проекцию списка и cursor strategy;
- инвентаризировать все текущие D1 Manager tables и миграционный runner;
- подготовить безопасные тестовые fixtures без Production writes.

### Этап B — D1 audit + API
- additive D1 migration для audit;
- owner-only audit GET;
- direct plant list/detail/create/update;
- idempotency и optimistic concurrency;
- unit tests role matrix и audit failure handling.

### Этап C — мобильный UI
- единый список, поиск, категории, карточки;
- единый редактор и галерея;
- варианты 1–30;
- BG/RU/EN descriptions/SEO;
- AI-enrich для всех ролей;
- owner-only botanical section;
- owner-only history.

### Этап D — регрессия и rollout
- проверка трёх ролей в отдельных authenticated sessions;
- создание тестового растения на Preview или безопасном изолированном dataset;
- редактирование существующего растения с восстановлением исходного значения после теста;
- проверка публичной карточки, варианта, корзины и заказа;
- проверка owner-only audit и невозможности доступа Seller/Manager;
- ручная мобильная приёмка на Android;
- после отдельного согласования — production migration/deploy.

### Обязательные критерии
1. Seller создаёт и публикует растение напрямую.
2. Manager редактирует любое существующее растение и публикует напрямую.
3. Owner выполняет те же операции и видит журнал.
4. Seller и Manager не видят и не могут запросить журнал (HTTP 403).
5. Seller и Manager не видят и не могут менять `plantCare`/`careGuide`.
6. Все роли используют AI-заполнение; цены/остатки/варианты не генерируются.
7. Карточка с несколькими вариантами сохраняет все `_key` и значения; публичный выбор варианта даёт правильную цену в корзине.
8. Основное изображение и галерея сохраняют порядок и ALT на трёх языках.
9. Конфликт _rev не перезаписывает чужие изменения.
10. Старые опубликованные товары, slug, категории и assets не теряются.
11. Незавершённые старые submissions сохраняются и не публикуются автоматически.
12. Заказы и существующие order snapshots продолжают работать.

## 12. Открытые вопросы / НЕ ИЗВЕСТНО — нужно уточнить

1. **Публичная логика root price vs saleVariants:** выборка уже выявила несовпадающие значения. Нужно пройти текущие storefront/cart/order источники и зафиксировать canonical/fallback до первого PATCH.
2. **Агрегация цены и наличия в Manager list:** показывать минимальную цену варианта, цену выбранного/первого варианта или диапазон; статус при смешанных вариантах. Рекомендация: отображать диапазон цены при разных ценах и статус «Различни варианти», но проверить удобство и публичную модель.
3. **Количество растений:** schema допускает number, текущая форма проверяет integer. Нужно проверить реальный учёт растений и решить, разрешены ли дробные количества.
4. **AI-модель и текущая квота:** использовать действующую Workers AI конфигурацию; точные модель/лимиты проверяются перед реализацией, не фиксируются предположительно.
5. **Authenticated тестовые аккаунты:** доступные отдельные Owner/Manager/Seller sessions для полного role matrix — НЕ ИЗВЕСТНО.
6. **Production D1 migration/deploy:** не разрешены этим ТЗ; потребуют отдельного подтверждения после Preview/CI.

## 13. Границы изменений

Не входит в задачу:
- Sanity dataset `production` и товары оборудования;
- оборудование Rain Bird и другие irrigation products;
- услуги, блог, service leads;
- Orders, checkout, delivery, Resend;
- Header, меню, Footer, публичная глобальная оболочка;
- изменение всех существующих прав на другие модули;
- удаление старых D1 таблиц/заявок/событий;
- массовая миграция Sanity документов;
- изменение Sanity schema без доказанной необходимости;
- production deployment до отдельного согласования.

**Итог:** Florial Manager становится прямым мобильным инструментом управления растениями. Sanity `plants` остаётся единственным каталогом товаров-растений; Cloudflare Pages Functions обеспечивает защищённые операции, Cloudflare D1 — авторизацию сотрудников и owner-only audit, а публичный магазин продолжает читать существующие Sanity документы без смены ID и URL.
