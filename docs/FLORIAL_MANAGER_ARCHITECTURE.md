# Florial Manager — архитектура закрытой приёмки товаров

**Статус:** проектирование, без изменений production  
**Дата:** 01.11.2026  
**Базовый commit:** `466a9e7913455a3ede5ddb86db2a3cbd637be16a`  
**Ветка:** `feature/florial-manager-architecture`

## 1. Цель

Создать закрытый внутренний интерфейс Florial Manager для приёмки новых товаров и подготовки изменений существующих товаров. Сотрудник создаёт предложение, прикладывает фотографии и коммерческие/технические данные, сохраняет черновик и отправляет его на проверку. Только владелец может окончательно одобрить и инициировать публикацию в Sanity.

Модуль должен поддерживать два каталога:
- `plants` — растения;
- `production` — оборудование для автоматического полива и основной каталог.

Первый эксплуатационный пилот — растения. Поддержка оборудования проектируется сразу, но подключается после проверки пилота.

## 2. Неприкосновенность публичного магазина

- Не добавлять ссылку Florial Manager в Header, меню, Footer, карточки товара или публичные CTA.
- Не менять публичную навигацию и глобальную оболочку ради панели.
- Не встраивать панель в текущий публичный компонент App: он формирует Header/Footer и считает неизвестные URL страницами 404.
- Предпочтительный вариант изоляции: отдельная точка выбора приложения в `src/main.tsx` по точному префиксу `/manager`. Для `/manager` и его внутренних маршрутов монтируется ManagerApp без публичного Header/Footer; для всех остальных URL сохраняется текущий App без изменений.
- Не полагаться на скрытый URL или robots.txt как на защиту. Защита обеспечивается аутентификацией и серверной авторизацией каждого API-запроса.
- Страницы панели должны отдавать noindex; это дополнительная мера, не контроль доступа.

## 3. Технологическая архитектура

| Слой | Ответственность |
|---|---|
| React + TypeScript | Отдельный интерфейс Manager, адаптированный для смартфонов |
| Supabase Auth | Персональные учётные записи сотрудников |
| Supabase Postgres | Черновики, предложения, статусы и журнал событий |
| Supabase Storage | Временные фотографии и документы приёмки в закрытом bucket |
| Cloudflare Pages Functions | Проверка сессии и ролей, API, уведомления, публикация |
| Sanity `plants` | Опубликованные карточки растений |
| Sanity `production` | Опубликованные карточки оборудования |
| Resend | Уведомление владельцу о новых предложениях |

Supabase service-role key и Sanity write token используются только серверными Cloudflare Functions. Они никогда не передаются в браузер.

## 4. Роли и полномочия

Роли хранятся в доверенном `app_metadata` или в серверно управляемом профиле, но не в редактируемом пользователем `user_metadata`.

| Роль | Возможности |
|---|---|
| `seller` | Создавать и редактировать собственные черновики, прикреплять фото, отправлять на проверку, видеть статусы собственных заявок |
| `manager` | Просматривать заявки сотрудников, проверять полноту, возвращать на исправление, оставлять комментарии; не публиковать |
| `owner` | Полный доступ, исправление данных, окончательное одобрение, публикация, управление пользователями и ролями |

Регистрация сотрудников публично закрыта. Учётные записи создаёт/приглашает владелец. Назначение роли — только серверная операция владельца. На первом запуске единственный publisher — владелец.

Каждый API endpoint повторно проверяет пользователя и роль. Скрытая кнопка или клиентская проверка не считаются авторизацией.

## 5. Модель заявок

Предлагаемые сущности в Supabase:

### `catalog_submissions`

- `id` UUID — идентификатор заявки;
- `catalog` — `plants` или `production`;
- `operation` — `create` или `update`;
- `target_document_id` — ID существующего Sanity-документа для обновления;
- `target_revision` — версия Sanity-документа, прочитанная при создании предложения;
- `payload` JSONB — подготовленные поля карточки / предлагаемые изменения;
- `status` — статус рабочего процесса;
- `created_by`, `reviewed_by` — UUID пользователей;
- `review_note` — комментарий проверяющего;
- `submitted_at`, `reviewed_at`, `published_at`;
- `publish_error` — безопасное диагностическое сообщение без секретов;
- `idempotency_key` — защита от повторной публикации;
- `created_at`, `updated_at`.

### `catalog_submission_events`

Неизменяемый журнал действий: заявка, пользователь, событие, прежний и новый статус, время, безопасные метаданные. Сотрудник не может переписывать историю событий.

### `catalog_staff_profiles` (при необходимости)

Профиль сотрудника для отображаемого имени и признака активности. Не является самостоятельным источником полномочий, если роль хранится в доверенном app_metadata.

Все таблицы включают RLS. Сотрудник видит и редактирует только собственные черновики; менеджер видит заявки в рамках разрешённых полномочий; владелец видит все. События и переходы критических статусов создаются сервером.

## 6. Статусы

Рекомендуемый конечный автомат:

- `draft` — черновик;
- `submitted` — отправлено владельцу/менеджеру;
- `in_review` — рассматривается;
- `changes_requested` — возвращено сотруднику;
- `approved` — владелец одобрил публикацию;
- `publishing` — сервер выполняет запись в Sanity;
- `published` — опубликовано и проверено;
- `publish_failed` — публикация не удалась, разрешён безопасный повтор после диагностики;
- `rejected` — отклонено.

Одобрение и успешная публикация — разные события. Нельзя показывать `published`, пока сервер не подтвердил запись и чтение результата из правильного Sanity dataset.

## 7. Создание и изменение товара

### Новый товар

1. Сотрудник выбирает каталог и категорию.
2. Заполняет доступные поля и добавляет фотографии.
3. Система проверяет возможный дубль по SKU и названию.
4. Черновик сохраняется в Supabase.
5. Сотрудник отправляет предложение.
6. Владелец проверяет, исправляет при необходимости и одобряет.
7. Сервер создаёт документ в целевом dataset Sanity.
8. Сервер повторно читает документ и проверяет ожидаемые ключевые поля.
9. Заявка получает статус `published`.

### Изменение существующего товара

1. Сотрудник находит товар по названию, SKU или Sanity ID.
2. Сервер загружает текущую карточку и её `_rev`.
3. В заявке хранятся исходные значения и предлагаемый payload.
4. Владелец видит сравнение «текущее / предложенное».
5. Перед публикацией сервер повторно проверяет исходную ревизию.
6. Если товар был изменён после создания заявки, публикация блокируется и требуется обновить предложение.
7. Сервер применяет только разрешённые поля; системные поля Sanity и не относящиеся к предложению данные не перезаписываются.

Для массивов вариантов продажи растений изменение должно адресоваться по стабильному `_key`, а не по номеру элемента. Нельзя заменять весь `saleVariants` без явного сравнения и подтверждения владельца.

## 8. Фотографии и файлы

- Для приёмки использовать закрытый Supabase Storage bucket.
- Bucket не публичный; файлы доступны только через серверно выданные временные signed upload/download URLs.
- Путь хранения привязывается к user ID и submission ID.
- Ограничить MIME-типы, размер, количество файлов и допустимые расширения; проверять содержимое файла, а не только имя.
- После одобрения Cloudflare Function переносит фото в соответствующий Sanity dataset и формирует корректные image references.
- Временные оригиналы сохраняются до подтверждения публикации и установленного срока хранения, затем могут очищаться отдельной процедурой.
- Не удалять исходники автоматически при ошибке публикации.

## 9. API Cloudflare Pages Functions

Предварительный набор маршрутов (точные имена файлов сверить с текущими соглашениями Pages Functions при реализации):

- `GET /api/manager/me` — текущая учётная запись и роль;
- `GET /api/manager/submissions` — список заявок в пределах прав;
- `POST /api/manager/submissions` — создать черновик;
- `GET /api/manager/submissions/:id` — получить заявку;
- `PATCH /api/manager/submissions/:id` — обновить собственный черновик;
- `POST /api/manager/submissions/:id/submit` — отправить на проверку;
- `POST /api/manager/submissions/:id/request-changes` — вернуть на исправление;
- `POST /api/manager/submissions/:id/approve` — одобрить владельцем;
- `POST /api/manager/submissions/:id/publish` — запустить/повторить публикацию после проверки полномочий;
- `POST /api/manager/uploads/sign` — получить одноразовую ссылку для загрузки;
- `POST /api/manager/uploads/:id/complete` — подтвердить загрузку и привязать файл к заявке.

API должен валидировать JSON по allowlist полей целевого типа, ограничивать размер запроса, проверять CSRF/origin и сессию, применять rate limits, безопасно логировать ошибки и использовать idempotency для публикации.

## 10. Уведомления

После успешного сохранения статуса `submitted` создаётся уведомление владельцу по email. Предусмотреть повторную отправку и состояние доставки. Уведомление содержит тип операции, каталог, название/SKU, автора, время и ссылку на закрытую панель; не прикладывать приватные файлы и не раскрывать секреты.

Для нового уведомления предпочтительно выделить переменную `CATALOG_REVIEW_EMAIL`. До настройки сверить реальные Cloudflare production/preview variables и существующие Resend sender settings. Не предполагать, что переменная уже существует или что email доставляется, пока это не проверено.

## 11. Интерфейс

Мобильная панель:
- вход;
- главная с количеством черновиков и заявок;
- «Добавить растение»;
- поиск существующего товара;
- форма товара с фотографированием камерой и галереей;
- варианты продажи растения (высота, контейнер, SKU, цена EUR с ДДС, наличие, количество);
- сохранение черновика и автосохранение;
- предварительный просмотр;
- отправка на проверку;
- список своих заявок и статусы.

Панель владельца:
- очередь заявок;
- фильтры по каталогу, статусу, сотруднику и дате;
- сравнение текущих и предложенных значений;
- просмотр фотографий;
- редактирование предложения;
- одобрение, возврат на исправление или отклонение;
- история событий и результат публикации.

Интерфейс внутренней системы — сначала болгарский; архитектура не должна мешать дополнительным RU/EN локализациям.
