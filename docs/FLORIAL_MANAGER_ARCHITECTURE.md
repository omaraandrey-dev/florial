# Florial Manager — архитектура закрытой приёмки товаров

**Статус:** первая версия объединена в main, production deployment и Supabase migration выполнены 01.11.2026  
**Дата:** 01.11.2026  
**Базовый commit:** `466a9e7913455a3ede5ddb86db2a3cbd637be16a`  
**Ветка:** `feature/florial-manager-architecture`

## 1. Цель

Создать закрытый внутренний интерфейс Florial Manager для приёмки новых товаров и подготовки изменений существующих товаров. Сотрудник создаёт предложение, прикладывает фотографии и коммерческие/технические данные, сохраняет черновик и отправляет его на проверку. Только владелец может окончательно одобрить и инициировать публикацию в Sanity.

Модуль должен поддерживать два каталога:
- `plants` — растения;
- `production` — оборудование для автоматического полива и основной каталог.

Первый эксплуатационный пилот — растения. Поддержка оборудования проектируется сразу, но подключается после проверки пилота.

## 2. Неприкосновенность публичного магазина

- Не добавлять ссылку Florial Manager в Header, меню, Footer, карточки товара или публичные CTA.
- Не менять публичную навигацию и глобальную оболочку ради панели.
- Не встраивать панель в текущий публичный компонент App: он формирует Header/Footer и считает неизвестные URL страницами 404.
- Предпочтительный вариант изоляции: отдельная точка выбора приложения в `src/main.tsx` по точному префиксу `/manager`. Для `/manager` и его внутренних маршрутов монтируется ManagerApp без публичного Header/Footer; для всех остальных URL сохраняется текущий App без изменений.
- Не полагаться на скрытый URL или robots.txt как на защиту. Защита обеспечивается аутентификацией и серверной авторизацией каждого API-запроса.
- Страницы панели должны отдавать noindex; это дополнительная мера, не контроль доступа.

## 3. Технологическая архитектура

| Слой | Ответственность |
|---|---|
| React + TypeScript | Отдельный интерфейс Manager, адаптированный для смартфонов |
| Supabase Auth | Персональные учётные записи сотрудников |
| Supabase Postgres | Черновики, предложения, статусы и журнал событий |
| Supabase Storage | Временные фотографии и документы приёмки в закрытом bucket |
| Cloudflare Pages Functions | Проверка сессии и ролей, API, уведомления, публикация |
| Sanity `plants` | Опубликованные карточки растений |
| Sanity `production` | Опубликованные карточки оборудования |
| Resend | Уведомление владельцу о новых предложениях |

Supabase service-role key и Sanity write token используются только серверными Cloudflare Functions. Они никогда не передаются в браузер.

## 4. Роли и полномочия

Роли хранятся в доверенном `app_metadata` или в серверно управляемом профиле, но не в редактируемом пользователем `user_metadata`.

| Роль | Возможности |
|---|---|
| `seller` | Создавать и редактировать собственные черновики, прикреплять фото, отправлять на проверку, видеть статусы собственных заявок |
| `manager` | Просматривать заявки сотрудников, проверять полноту, возвращать на исправление, оставлять комментарии; не публиковать |
| `owner` | Полный доступ, исправление данных, окончательное одобрение, публикация, управление пользователями и ролями |

Регистрация сотрудников публично закрыта. Учётные записи создаёт/приглашает владелец. Назначение роли — только серверная операция владельца. На первом запуске единственный publisher — владелец.

Каждый API endpoint повторно проверяет пользователя и роль. Скрытая кнопка или клиентская проверка не считаются авторизацией.

## 5. Модель заявок

Предлагаемые сущности в Supabase:

### `catalog_submissions`

- `id` UUID — идентификатор заявки;
- `catalog` — `plants` или `production`;
- `operation` — `create` или `update`;
- `target_document_id` — ID существующего Sanity-документа для обновления;
- `target_revision` — версия Sanity-документа, прочитанная при создании предложения;
- `payload` JSONB — подготовленные поля карточки / предлагаемые изменения;
- `status` — статус рабочего процесса;
- `created_by`, `reviewed_by` — UUID пользователей;
- `review_note` — комментарий проверяющего;
- `submitted_at`, `reviewed_at`, `published_at`;
- `publish_error` — безопасное диагностическое сообщение без секретов;
- `idempotency_key` — защита от повторной публикации;
- `created_at`, `updated_at`.

### `catalog_submission_events`

Неизменяемый журнал действий: заявка, пользователь, событие, прежний и новый статус, время, безопасные метаданные. Сотрудник не может переписывать историю событий.

### `catalog_staff_profiles` (при необходимости)

Профиль сотрудника для отображаемого имени и признака активности. Не является самостоятельным источником полномочий, если роль хранится в доверенном app_metadata.

Все таблицы включают RLS. Сотрудник видит и редактирует только собственные черновики; менеджер видит заявки в рамках разрешённых полномочий; владелец видит все. События и переходы критических статусов создаются сервером.

## 6. Статусы

Рекомендуемый конечный автомат:

- `draft` — черновик;
- `submitted` — отправлено владельцу/менеджеру;
- `in_review` — рассматривается;
- `changes_requested` — возвращено сотруднику;
- `approved` — владелец одобрил публикацию;
- `publishing` — сервер выполняет запись в Sanity;
- `published` — опубликовано и проверено;
- `publish_failed` — публикация не удалась, разрешён безопасный повтор после диагностики;
- `rejected` — отклонено.

Одобрение и успешная публикация — разные события. Нельзя показывать `published`, пока сервер не подтвердил запись и чтение результата из правильного Sanity dataset.

## 7. Создание и изменение товара

### Новый товар

1. Сотрудник выбирает каталог и категорию.
2. Заполняет доступные поля и добавляет фотографии.
3. Система проверяет возможный дубль по SKU и названию.
4. Черновик сохраняется в Supabase.
5. Сотрудник отправляет предложение.
6. Владелец проверяет, исправляет при необходимости и одобряет.
7. Сервер создаёт документ в целевом dataset Sanity.
8. Сервер повторно читает документ и проверяет ожидаемые ключевые поля.
9. Заявка получает статус `published`.

### Изменение существующего товара

1. Сотрудник находит товар по названию, SKU или Sanity ID.
2. Сервер загружает текущую карточку и её `_rev`.
3. В заявке хранятся исходные значения и предлагаемый payload.
4. Владелец видит сравнение «текущее / предложенное».
5. Перед публикацией сервер повторно проверяет исходную ревизию.
6. Если товар был изменён после создания заявки, публикация блокируется и требуется обновить предложение.
7. Сервер применяет только разрешённые поля; системные поля Sanity и не относящиеся к предложению данные не перезаписываются.

Для массивов вариантов продажи растений изменение должно адресоваться по стабильному `_key`, а не по номеру элемента. Нельзя заменять весь `saleVariants` без явного сравнения и подтверждения владельца.

## 8. Фотографии и файлы

- Для приёмки использовать закрытый Supabase Storage bucket.
- Bucket не публичный; файлы доступны только через серверно выданные временные signed upload/download URLs.
- Путь хранения привязывается к user ID и submission ID.
- Ограничить MIME-типы, размер, количество файлов и допустимые расширения; проверять содержимое файла, а не только имя.
- После одобрения Cloudflare Function переносит фото в соответствующий Sanity dataset и формирует корректные image references.
- Временные оригиналы сохраняются до подтверждения публикации и установленного срока хранения, затем могут очищаться отдельной процедурой.
- Не удалять исходники автоматически при ошибке публикации.

## 9. API Cloudflare Pages Functions

Предварительный набор маршрутов (точные имена файлов сверить с текущими соглашениями Pages Functions при реализации):

- `GET /api/manager/me` — текущая учётная запись и роль;
- `GET /api/manager/submissions` — список заявок в пределах прав;
- `POST /api/manager/submissions` — создать черновик;
- `GET /api/manager/submissions/:id` — получить заявку;
- `PATCH /api/manager/submissions/:id` — обновить собственный черновик;
- `POST /api/manager/submissions/:id/submit` — отправить на проверку;
- `POST /api/manager/submissions/:id/request-changes` — вернуть на исправление;
- `POST /api/manager/submissions/:id/approve` — одобрить владельцем;
- `POST /api/manager/submissions/:id/publish` — запустить/повторить публикацию после проверки полномочий;
- `POST /api/manager/uploads/sign` — получить одноразовую ссылку для загрузки;
- `POST /api/manager/uploads/:id/complete` — подтвердить загрузку и привязать файл к заявке.

API должен валидировать JSON по allowlist полей целевого типа, ограничивать размер запроса, проверять CSRF/origin и сессию, применять rate limits, безопасно логировать ошибки и использовать idempotency для публикации.

## 18. Управление сотрудниками владельцем — 01.11.2026

### Интерфейс

- В `src/manager/ManagerApp.tsx` добавлена вкладка «Сотрудники», отображаемая только активному пользователю с ролью `owner`.
- Поддерживаются: список сотрудников, email и статус, создание `seller`/`manager`, изменение роли, установка нового пароля владельцем, отключение и восстановление доступа.
- Учетная запись с ролью `owner` не может быть изменена из этой панели; создание дополнительных owner-аккаунтов не предусмотрено.
- Физическое удаление не используется: деактивация сохраняет профиль и связанные заявки.

### Серверная граница

- Endpoint: `/api/manager/staff` (Cloudflare Pages Function).
- `GET`: возвращает только безопасные поля профиля и email из Supabase Auth.
- `POST`: создаёт Auth user через Admin API, затем создаёт `catalog_staff_profiles`; если профиль не сохранился, созданный в этой операции Auth user откатывается.
- `PATCH`: меняет роль/имя, пароль через Auth Admin API, либо `is_active`.
- Каждый запрос сначала проверяет bearer-сессию через `/auth/v1/user`, затем активную роль `owner` из серверно управляемой таблицы.
- Service role key используется только в Cloudflare Pages Function; браузеру возвращаются только безопасные данные.
- При отключении доступ к Manager блокируется действующими RLS policies через `private.has_catalog_role`, который проверяет `is_active=true`.

### Ограничение паролей

В интерфейсе нет self-service password change/recovery, а все операции установки пароля в Manager доступны только owner. Однако Supabase Auth по умолчанию предоставляет авторизованному пользователю endpoint обновления собственных атрибутов, включая пароль. Отдельного штатного Auth hook для блокировки именно этого обновления в используемой конфигурации не подтверждено. Поэтому абсолютное ограничение прямого Auth API не заявляется; для него потребуется отдельная архитектура авторизации.

- Новая SQL migration не требуется: используются существующие таблицы и RLS.
- Не изменяются Header, menu, Footer, публичные страницы, checkout, заказы, Sanity и Cloudflare variables.
- Preview secrets не добавляются.

## 20. Проверка владельцем до запуска ИИ — 01.11.2026

### Согласованный рабочий процесс

1. Продавец создаёт заявку и отправляет её владельцу. Сохранение черновика, загрузка фото, отправка и открытие заявки не вызывают ИИ.
2. Владелец открывает заявку со статусом submitted или in_review, видит фотографии и получает редактируемую карточку. Он проверяет и исправляет название, ботаническое имя, категорию, SKU, описание, вариант продажи, цену, высоту, объём контейнера, количество и наличие.
3. Только явное нажатие владельцем «Подготви карточката с ИИ» вызывает POST /api/manager/enrich-plant. В запрос передаются проверенные владельцем исходные значения. ИИ не вызывается автоматически.
4. AI-черновик сохраняется отдельно в payload.aiDraft; исходный payload продавца не перезаписывается. Цена, SKU, высота при продаже, объём контейнера, статус наличия и количество копируются из проверенных владельцем значений и не генерируются моделью.
5. Владелец редактирует AI-результат и сохраняет карточку в payload.publication. Кнопка одобрения доступна только после сохранения подготовленной карточки.
6. После одобрения открывается обычный этап публикации. Кнопка публикации появляется только для статусов approved и publish_failed; только она вызывает запись документа в Sanity.

### Защита от лишних расходов и ошибок

- Ни продавец, ни менеджер не могут запустить AI endpoint: сервер проверяет активную роль owner.
- AI endpoint принимает заявки на этапе submitted / in_review, а также прежние разрешённые статусы для совместимости.
- Если payload.aiDraft уже существует, endpoint возвращает сохранённый результат с признаком повторного использования и не запускает модель снова. Кнопка повторной генерации в интерфейсе отключена.
- Открытие заявки, просмотр фото, редактирование полей, сохранение карточки и одобрение не запускают AI.
- Сохранение подготовленной карточки допускается до одобрения, но endpoint публикации не позволяет опубликовать товар до статуса approved.
- Существующая схема Supabase, RLS, Sanity schema и данные каталога не меняются. SQL migration не требуется. Публичный магазин, checkout, Header/menu/Footer не затрагиваются.

### Разделение данных

- payload — оригинальная заявка продавца и её фотографии.
- payload.aiDraft — результат единственного явного запуска AI.
- payload.publication — версия карточки, проверенная и сохранённая владельцем для одобрения и последующей публикации.

## 21. Диагностика ошибок AI — 01.11.2026

- Endpoint `/api/manager/enrich-plant` отслеживает текущий этап выполнения: проверка, загрузка фото, vision inference, разбор ALT JSON, генерация текста, разбор результата и сохранение черновика.
- При ошибке endpoint возвращает диагностический ID, этап, номер фото (если применимо), код классификации, понятное пояснение и ограниченный технический ответ модели.
- Ошибки записываются в существующий `catalog_submission_events` как `ai_draft_failed`. Успешный вызов по-прежнему записывается как `ai_draft_generated`.
- В журнал не попадают фото, base64, access tokens, service-role key или другие секреты. Техническое сообщение ограничено по длине.
- UI Manager показывает владельцу этап и диагностический код; повторная генерация не запускается автоматически.
- Исправление не требует SQL migration, не изменяет структуру данных, Sanity, публичный каталог и исходный payload продавца.
- Лицензию Meta для модели Llama 3.2 Vision требуется принять отдельно на уровне Cloudflare account до первого inference. Сам Manager не принимает лицензию автоматически и не выполняет скрытый AI-запрос при открытии заявки.

## 22. Устойчивый разбор ответов Vision для ALT — 01.11.2026

- Vision-вызов просит одно краткое описание видимых деталей на болгарском языке обычным текстом, а не JSON.
- Полученное описание передаётся в текстовый этап как визуальное наблюдение. Текстовый этап подготавливает переводы ALT на BG/RU/EN в том же порядке фотографий.
- Причина предыдущего сбоя: Vision-вызов завершался, но ответ не содержал JSON-объект, который ожидал прежний парсер. Это приводило к остановке до генерации описания растения.
- Изменение не меняет коммерческие поля, исходный payload продавца, схему Supabase, Sanity или публичный каталог.


## 23. Структурированный ответ текстовой AI-модели — 01.11.2026

- Для текстовой генерации карточки используется отдельная Workers AI модель `@cf/meta/llama-3.1-8b-instruct`, поддерживающая JSON Mode.
- Запрос включает `response_format: { type: 'json_object' }`, явный `max_tokens: 4096` и пониженную температуру, чтобы снизить вероятность невалидного или оборванного JSON.
- Vision-модель остаётся отдельным этапом и возвращает краткое текстовое описание каждой фотографии.
- Диагностика фиксирует модель, соответствующую этапу сбоя, без сохранения содержимого фотографий, base64 или секретов.
- Изменение не требует миграции Supabase, изменения схемы Sanity или обновления публичного каталога.

## 2026-11-03 — Granular authorization model

The earlier owner-only descriptions in this document are superseded by the permission model below.

Manager authorization is based on the active D1 staff profile and ten boolean permissions stored in `catalog_staff_profiles.permissions`: `canCreatePlant`, `canEditPlantCard`, `canAddPlantVariant`, `canEditPlantPrice`, `canReviewPlantSubmissions`, `canApprovePlantSubmission`, `canPublishPlant`, `canManageStaff`, `canDelegatePermissions`, and `canViewAnalytics`.

The owner role has all rights automatically. A manager must have `canManageStaff` to manage directly-created staff and `canDelegatePermissions` to assign a subset of their own rights or create another manager. The server rejects permission escalation and prevents managers from changing the owner account. Permission changes are logged in `catalog_staff_permission_events`.

Approval and publication are separate. `canApprovePlantSubmission` approves a prepared submission; `canPublishPlant` publishes only an approved submission to Sanity. Final-card preparation and related AI actions require `canEditPlantCard`. Every protected operation is checked by its Cloudflare API endpoint.

Production D1 migration `0006_manager_permissions` adds the staff creator relationship, normalizes existing permissions, strengthens permission triggers and creates the permission audit table. Existing staff, sessions, submissions and catalog data are retained.

### Separate approval and publication for existing catalog changes

Requests to add a plant variant or edit a price now follow `submitted/in_review → approved → published`. Approval validates the Sanity document revision and requires `canApprovePlantSubmission`; it does not mutate Sanity. The subsequent publication requires `canPublishPlant`. Publication is retry-safe: if Sanity already contains the exact requested change but the D1 status update previously failed, the endpoint confirms the applied change and completes the status transition without duplicating it.

If a previously approved new-plant card is edited, its status returns to `in_review` and approval must be repeated. The generic Manager data endpoint cannot set `published`, `publishing`, `publish_failed`, or approve existing-catalog changes.
